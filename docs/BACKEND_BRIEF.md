# Backend Implementation Brief — Spring Boot API

This is the authoritative, detailed spec for `/backend`. It expands on `portfolio-platform-spec.md`
with exact entities, endpoints, config, and seed data. Follow it precisely; where it's silent, use
sound Spring Boot 3 conventions.

## 2. Entities & Flyway migrations

Put migrations in `src/main/resources/db/migration`, `V1__init_schema.sql`, `V2__seed_initial_data.sql`,
etc. Use `snake_case` table/column names, `bigserial` PKs, `timestamptz` for timestamps
(`created_at`/`updated_at`, auto-managed via `@CreationTimestamp`/`@UpdateTimestamp` or `@PrePersist`).

- **`admin_user`** — `id`, `username` (unique), `password_hash`, `role` (varchar, values `ADMIN`),
  `created_at`, `updated_at`.
- **`refresh_token`** — `id`, `admin_user_id` FK, `token_hash` (store SHA-256 hash, not raw token),
  `expires_at`, `revoked` (bool default false), `created_at`.
- **`profile`** — singleton row (just always use id=1 or enforce single row in service layer):
  `id`, `full_name`, `title`, `tagline`, `bio` (text), `email`, `phone`, `location`, `github_url`,
  `linkedin_url`, `twitter_url`, `website_url`, `avatar_media_id` FK→media nullable,
  `resume_media_id` FK→media nullable, `updated_at`.
- **`page`** — `id`, `slug` (unique — `home`, `about`, `projects`, `experience`, `education`, `skills`,
  `contact`), `title`, `meta_title`, `meta_description`, `updated_at`.
- **`section`** — belongs to a page, generic enough that new sections never require new entity types:
  `id`, `page_id` FK, `section_key` (varchar — free-form slug like `hero`, `intro`, `cta`, unique per
  page), `heading`, `subheading`, `description` (text, rich/HTML-safe string), `section_type` (varchar,
  default `GENERIC` — e.g. `HERO`, `CTA`, `GALLERY`, `GENERIC`), `order_index` (int), `visible` (bool
  default true), `content_json` (text — arbitrary JSON blob for section-type-specific extra fields,
  nullable), `created_at`, `updated_at`.
- **`section_image`** — join table for multi-image sections: `id`, `section_id` FK, `media_id` FK,
  `order_index`, `caption` nullable.
- **`project`** — `id`, `title`, `slug` (unique), `summary` (varchar 500), `description` (text),
  `client_name` (varchar nullable — e.g. "British American Tobacco"), `category` (varchar nullable),
  `status` (varchar — `COMPLETED` | `IN_PROGRESS`, default `COMPLETED`), `repo_url` nullable,
  `live_url` nullable, `featured` (bool default false), `order_index` (int), `start_date` (date
  nullable), `end_date` (date nullable), `created_at`, `updated_at`.
- **`project_tech_tag`** — `project_id` FK, `tag` (varchar) — simple `@ElementCollection` table, no
  separate entity needed.
- **`project_image`** — `id`, `project_id` FK, `media_id` FK, `order_index`, `is_cover` (bool default
  false).
- **`skill_category`** — `id`, `name`, `order_index`.
- **`skill`** — `id`, `skill_category_id` FK, `name`, `proficiency` (int 0–100), `icon` (varchar
  nullable — icon name/class, not necessarily a Media), `order_index`.
- **`experience`** — `id`, `company`, `role`, `location` nullable, `start_date` (date), `end_date`
  (date nullable = present), `description` (text), `company_logo_media_id` FK→media nullable,
  `order_index`.
- **`education`** — `id`, `institution`, `degree`, `field` nullable, `start_date` (date nullable —
  some CV entries only have a year), `end_date` (date nullable), `description` nullable, `order_index`.
  (If only a year is known, store Jan 1 of that year and note precision is year-only via a
  `date_precision` varchar column: `YEAR` | `MONTH_YEAR` | `FULL`, default `FULL` — the admin UI will
  respect this when rendering date pickers.)
- **`media`** — `id`, `stored_file_name`, `original_file_name`, `url` (public path, e.g.
  `/uploads/2026/08/uuid-name.jpg`), `content_type`, `size_bytes`, `alt_text` nullable,
  `linked_entity_type` nullable, `linked_entity_id` nullable, `uploaded_at`.
- **`contact_message`** — `id`, `name`, `email`, `subject` nullable, `message` (text), `is_read` (bool
  default false), `created_at`.
- **`site_settings`** — singleton: `id`, `seo_default_title`, `seo_default_description`,
  `theme_accent_color` (varchar, hex), `updated_at`.

## 3. Auth (JWT)

- `POST /api/auth/login` — body `{username, password}` → `{accessToken, refreshToken, expiresIn,
  user: {id, username, role}}`. Verify password with BCrypt.
- `POST /api/auth/refresh` — body `{refreshToken}` → new access+refresh pair. Rotate refresh tokens:
  on use, revoke the old `refresh_token` row and insert a new one (store only the SHA-256 hash of the
  token value, never the raw token, matching the pattern used for `password_hash`).
- Access tokens: JWT signed HS256 with `JWT_SECRET`, short TTL, claims include `sub` (username), `role`,
  `uid`.
- Spring Security: stateless, JWT filter validates `Authorization: Bearer <token>` on `/api/admin/**`;
  `/api/public/**`, `/api/auth/**`, and `/v3/api-docs*/**` + `/swagger-ui/**` are permitted without auth.
  Disable CSRF (stateless JWT API). BCrypt password encoder bean.
- No self-registration endpoint — only the seeded admin user exists.

## 4. API surface

Every admin-prefixed route requires a valid JWT. Every public/auth route does not.

```
Auth
  POST   /api/auth/login
  POST   /api/auth/refresh

Public (read-only)
  GET    /api/public/profile
  GET    /api/public/pages/{slug}                 -> page + its visible sections (ordered), each section's images
  GET    /api/public/projects?category=&featured=  -> ordered list
  GET    /api/public/projects/{slug}
  GET    /api/public/skills                        -> grouped by category, ordered
  GET    /api/public/experience                     -> ordered
  GET    /api/public/education                      -> ordered
  GET    /api/public/settings                        -> SEO defaults / theme accent
  POST   /api/public/contact                        -> validated create, no auth, rate-limit not required

Admin (JWT required)
  GET/PUT     /api/admin/profile
  GET         /api/admin/pages                       -> list all pages (id, slug, title)
  GET/PUT     /api/admin/pages/{pageId}
  GET/POST    /api/admin/pages/{pageId}/sections
  GET/PUT/DELETE /api/admin/pages/{pageId}/sections/{sectionId}
  PATCH       /api/admin/pages/{pageId}/sections/reorder     body: [{id, orderIndex}]
  POST/DELETE /api/admin/pages/{pageId}/sections/{sectionId}/images   (attach/detach a media item)

  GET/POST    /api/admin/projects                    (GET supports page/size/search/category query params)
  GET/PUT/DELETE /api/admin/projects/{id}
  PATCH       /api/admin/projects/reorder             body: [{id, orderIndex}]
  POST/DELETE /api/admin/projects/{id}/images         (attach/detach gallery media, set cover)

  GET/POST    /api/admin/skill-categories
  PUT/DELETE  /api/admin/skill-categories/{id}
  GET/POST    /api/admin/skills
  PUT/DELETE  /api/admin/skills/{id}

  GET/POST    /api/admin/experience
  PUT/DELETE  /api/admin/experience/{id}

  GET/POST    /api/admin/education
  PUT/DELETE  /api/admin/education/{id}

  POST        /api/admin/media/upload                multipart, field "file" + optional altText
  GET         /api/admin/media                        (page/size/search)
  DELETE      /api/admin/media/{id}

  GET         /api/admin/messages                     (page/size/unreadOnly)
  PATCH       /api/admin/messages/{id}/read
  DELETE      /api/admin/messages/{id}

  GET/PUT     /api/admin/settings

  GET         /api/admin/dashboard/summary            -> {unreadMessagesCount, totalProjects,
                                                            totalSections, totalMedia, lastEditedSection}
```

Static file serving: register a resource handler mapping `STORAGE_PUBLIC_PATH` (`/uploads/**`) to
`file:${STORAGE_BASE_PATH}/`, so `media.url` values are directly fetchable.

List responses for admin screens with potentially many rows (`projects`, `media`, `messages`) should
support Spring Data `Pageable` (`page`, `size`, `sort` query params) and return
`{content, totalElements, totalPages, number, size}`. Small, bounded lists (`skills`, `experience`,
`education`, `sections`) can just return plain ordered arrays.

Document everything via springdoc — `/swagger-ui.html` should show every endpoint grouped sensibly
(Auth, Public, Admin: Profile/Pages/Projects/Skills/Experience/Education/Media/Messages/Settings).

## 5. File storage abstraction

Define a `StorageService` interface:
```java
public interface StorageService {
    StoredFile store(MultipartFile file, String subfolder);
    void delete(String storedFileName);
}
```
`LocalDiskStorageService` is the only implementation for now — writes under
`${STORAGE_BASE_PATH}/{yyyy}/{MM}/{uuid}-{sanitized-original-name}`, returns a `StoredFile` (stored
name, public url, content type, size). Keep this behind the interface so a future
`S3StorageService`/`CloudinaryStorageService` is a drop-in swap (a `@ConditionalOnProperty` on
`app.storage.type` is a nice touch but not required). Validate uploads: allowed content types
`image/jpeg, image/png, image/webp, image/gif, application/pdf`; max size 10MB (reject with a 400 and
clear message otherwise).

When deleting a `Media` row: null out any `profile.avatar_media_id`/`resume_media_id`,
`experience.company_logo_media_id`, and remove any `section_image`/`project_image` rows referencing it
*before* deleting the row and the underlying file, to avoid FK violations or orphaned references.

## 6. Cross-cutting

- Bean Validation (`@NotBlank`, `@Email`, `@Size`, etc.) on every request DTO; return a consistent
  error body from a `@RestControllerAdvice`:
  `{timestamp, status, error, message, path, validationErrors: [{field, message}]?}`.
- Manual mapper methods (static factory methods on response DTOs, e.g. `ProjectResponse.from(Project
  entity)`) are preferred over MapStruct here — keep the dependency footprint small and avoid
  annotation-processor build friction.
- CORS configured from `CORS_ALLOWED_ORIGINS`.
- Keep controllers thin — validation + delegation; services own business logic and transactions
  (`@Transactional` on write paths).
